# v0.2.20-Leap 方控排查记录

核对来源：https://github.com/Wh1t3co1azZ/DiPlay-Leapmotor/blob/v0.2.20-Leap/common/src/main/java/com/shilapi/xcertplay/LeapmotorMediaKeys.kt

已确认的源码事实：

1. EXTRA_CHANNELS 定义了 com.leapmotor.ICU2MMICtrl 和 com.leapmotor.customkey.music.pauseplay，但 attach 只注册 ACTIONS，ACTIONS 不包含 EXTRA_CHANNELS。采用这些通道的固件无法走到对应解析代码。
2. c11ChannelAction 用 getStringExtra 读取 value，只接受字符串 1/2/3；整数相同数值不匹配。车主具体字段类型尚未采集。
3. 接收器使用 ContextCompat.RECEIVER_NOT_EXPORTED。OEM 媒体服务若不属于允许的系统发送者，接收范围可能不足。Android 官方说明：https://developer.android.com/develop/background-work/background-tasks/broadcasts 。具体固件的发送 UID 与权限尚未确认。
4. 方控媒体键与音量键可走不同通路，所以原车音量正常不足以证明媒体广播正常。

新方案注册完整的已知媒体 action 列表，同时支持字符串和整型 C11 值，对来自其它 UID 的媒体广播使用 EXPORTED，但仅解析白名单中的媒体命令。裸 play/pause/stop、后排、音量和车辆控制命令不转发；对无会话、关闭转发、畸形载荷和重复事件均有处理。EXPORTED 不保证发送者真实性，本适配仅作用于媒体播放；其它应用可能伪造媒体广播，因此默认关闭，且不会将此接收器用于任何车辆控制。

这些源码缺口提供了合理排查方向，并非已经确认车主车辆的真实根因。仍需在车机界面导出诊断，对照实际通道、值与发送结果。所有车机 ADB 操作须单独批准。

车主进一步确认的实际现象：在原 Leap21_23 中按方向盘媒体键，车机网易云能响应，但 CarPlay 无响应。因此不能把当前故障描述为两个播放器都已响应；优先验证 DiPlay 的广播接收与解析，然后再核查是否存在原车播放器误触发。原车按键有效不代表 DiPlay 必然收到相同通道。

## 仪表完全不显示的源码排查

车主确认旧分支仪表完全不显示 CarPlay 导航。精确 tag 的 LeapmotorClusterLayout 做了 1920×720 面板右侧 720×720 视口，但 ClusterMapPresentation.findDisplay 仍沿用比亚迪的屏幕名识别；CarPlayHostActivity 对非 DiLink 5.1 的流尺寸也未明确切换为零跑方形流。因此只补渲染视口不足以证明仪表通路接通。

本项目补充公开屏幕的明确手动选择、匹配平台与几何限制、720×720 仪表流、右侧限界窗口和诊断。默认不选择、不给屏幕号设猜测值；私有屏幕、主屏、错误几何与重名均不能自动投屏。不采用 ADB task routing 或写车辆总线。仍需车机提供真实显示列表并由车主确认目标屏。

## LeapOS 1.15.10 实车反馈与 c11.3 互斥

2026-10-21，车主提供 c11.2 报告，包名 com.c11.diplay，Android 9/API28，QTI msmnile_gvmq。无线 CarPlay 建立且显示零跑图标。实际方控通道为 com.leapmotor.action.METER.CTRL，keyEventType=steeringWheel(String)，value=1/2/3(String)，分别成功解析 PREVIOUS/NEXT/TOGGLE。开启转发后车主确认 CarPlay 响应，但原车网易云同步播放，产生双重声音。此车的已观测字段是字符串；不能将参考源码的整型解析缺口直接称为本车根因。

同一报告在首次按键时出现 audio focus change=-1；这证明该时刻丢失音频焦点，不能仅凭这条日志确定哪个包申请焦点。旧去重只限制本应用转发，不拦截其它接收者。

c11.3 采用通知访问授权下的标准 MediaSessionManager.getActiveSessions 与定向 TransportControls.pause/play。只识别列出的音乐应用包名，不写整车音量、不禁用应用、不使用 CAN/ADB、不改系统文字或字体。默认关闭。连接期间约750ms检查，按键时即时追加检查；OEM忽略标准暂停、没有标准会话或使用未知包名时仍可能失败，不能宣称零延迟静音或已实车解决。

恢复仅面向开始监听时正在播放、已成功请求暂停且断开时仍活跃/暂停的同一个会话。开始监听时暂停或后来新出现的播放器不自动启动。权限断开、异常、通话、进程终止时不自动恢复，通过不修改任何音量或应用启用状态避免留下持久静音。主程序被强杀后的音乐可手动恢复。

通知使用权由车主在系统正常界面手动授权；无需第二个APK。类中不读取通知正文，只使用授权访问媒体会话。诊断仅输出媒体会话包名、状态与控制结果，不输出通知正文。

## c11.3 新实车反馈（待诊断）

车主反馈音乐互斥与方控开启后仍双响，CarPlay通话对方听不到声音；#1识别标记出现在副驾，#2标记不可见。照片显示仪表仍显示原车内容，无法据此确认普通Presentation能显示或确定其窗口坐标。不得按排除法直接将#2判为可用仪表，不得将#1选为仪表。

源码现有麦克风链路包含权限、音源选择、录音路由、捕获电平及UDP发送诊断；需要包含实际通话的新报告区分未请求麦克风、录音失败/全零、路由与发送问题。音乐互斥需要核对access/listenerConnected/monitoring及sessions包名、状态、pause requested是否出现；权限页面照片不能证明服务已绑定，pause requested也不证明播放器实际暂停。无证据前不修改系统音源/隐藏接口、不强制静音整车音量、不用ADB获取数据。

## c11.3 报告的确证与 c11.4 修正

车主报告确认：access=true listenerConnected=true monitoring=true；com.netease.cloudmusic.iot 被识别为supported=true，状态2/3/6变化，但全文无C11 music pause请求。源码normal-mode判断使MODE_IN_COMMUNICATION(3)时所有音乐暂停被跳过。日志多次“mode restored ... now=3”支持该条件会在结束通话后继续阻塞。c11.4移除对音乐定向暂停的普通模式要求，保留恢复的保守通话保护，并在诊断输出audioMode。

多次实际通话：VOICE_COMMUNICATION、routedDeviceType=15、有captureBytes/udpSent、readErrors=0/sendErrors=0，但peakDbfs=silent，证明源端采集为静音；不能断言只改音源一定恢复。增加用户可回退的C11专用通话音源选择，默认保留上游；只在下次通话创建录音器时生效，排除其它车型和非通话录音。源名称写入实际诊断，创建失败仍沿用上游既有fallback。

#1为副驾来自车主肉眼确认；#2未知。旧“instrument visually confirmed”只是用户点击确认产生，报告曾交替确认1/2，不能把它当硬件识别证据。新增标记窗口创建及不可证实物理可见的说明，移动小标记到右上角以排查原下角可见区域问题。不强制路由。
